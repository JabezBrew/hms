# Source-linked as-needed medication scope

The legacy prescription model marks frequency `prn`, and its nursing scheduler
creates no automatic dose times. It has no typed interval or daily maximum;
Python's four-potential-doses display heuristic is not a prescribing limit.
This implementation adds explicit safety limits without inferring defaults.

## Prescribing and stock basis

An optional `prn_policy` contains `minimum_interval_hours` (4, 6, 8, 12 or 24),
`maximum_doses_per_24_hours` (1 through 24 / interval), required trimmed
`indication` (up to 500 characters), and positive whole `stock_units_per_dose`.
The request also requires `expected_stock_unit` from the selected catalog item.
It is compared under the item shared lock before insertion, so a catalog correction
cannot silently reinterpret the amount the prescriber reviewed. Stock units are
bounded by JavaScript's exact integer range. Rust captures the
linked active, local, noncontrolled medication item's unit under a shared lock;
the client cannot override it. A configured PRN regimen is immutable. Stop it
and prescribe a replacement to change the drug, dose, stock basis or limits.
Legacy orders without a policy stay readable and cannot request PRN doses.

Fractional inventory units and controlled PRN stock are not implemented. The UI
must explain those limits without implying a separate available controlled PRN
workflow. The shared pharmacy dispenser still needs one unexpired batch large
enough for the whole requested issue; it does not silently issue partial or
multiple-batch supply. Normal scheduled prescribing retains its existing contract.

The prescriber explicitly selects the facility product, enters every PRN limit
and reviews the stock unit. Changing product, unit or controlled status clears
those limits. An explicit stale-unit conflict clears the binding and requires a
new catalog selection. Missing or different saved limits stay unconfirmed and
block another create. Patient/admission switches remount the draft; a late old
save cannot close or toast success over another patient's draft.

Existing inpatient encounters and historical `finished` encounters remain
readable through the typed clinical context used by prescribing. Canonical
completed list filters also include the historical spelling.

## One dose and an actual outcome

`GET /api/v2/nursing/prn-orders` requires an admission and authorizes its patient
before returning a bounded, descending source-order cursor page. Patient and PRN
frequency filters apply before LIMIT, so unrelated recent orders cannot obscure
older PRN prescriptions. Eligibility is informative; every write rechecks it.

`POST /api/v2/nursing/prn-dose-requests` accepts the source prescription,
admission, a stable client UUID, and the actual indication for this dose. It
locks the source prescription before verifying the active matching admission,
policy, stock unit and course snapshot. It initializes a course if needed and
creates one linked scheduled MAR row plus the ordinary pharmacy fulfillment.
Only one unresolved scheduled dose may exist per source prescription across
admissions. Identical same-actor UUID replay returns that original record
without a second request or audit, including after its outcome or source stop.
Changed payloads cannot reuse the reference.

The minimum interval and rolling 24-hour maximum use actual administered times
across the source prescription, including other admissions. Requests reserve the
one pending dose; administration checks actual limits again. The prescription
lock serializes requests, supply, source status changes and dose outcomes.
Admission and item shared locks prevent closure or unit changes racing a write.
Explicit source start, first-dose and duration bounds remain authoritative.
A planner's old generation preview window does not invent PRN expiry.

Pharmacy supplies an explicit number of doses. Stock movement and dispensing
quantities equal doses multiplied by the saved whole units per dose, using
checked arithmetic. Expired lots and inactive or foreign dispensing locations
cannot supply medication. A unit correction, stale course or inactive source
blocks supply and administration. Fulfillment reopens preserve supplied counts,
actors, timestamps and all earlier MAR history. Refused, held and missed decisions
do not claim administration or undo stock previously supplied.

The existing explicit `/outcome` operation records Administered/Missed/Refused/Held.
A sourced administered dose requires recorded pharmacy supply. Anonymous
create-and-administer is unavailable in the Rust UI; explicit unlinked `prn`
scheduling/outcomes also fail closed. Other existing manual scheduled-dose
compatibility is retained.

## Client confirmation and cache behavior

The admission-keyed MAR workspace contains the PRN order panel. It shows the
prescriber limits, indication, units per dose, actual recent count and outstanding
request. Each form generates one UUID, requires an actual indication and disables
automatic retries. An uncertain response blocks another submission pending review.
The pharmacy client validates response identity and dose counts before claiming
supply, also disables retries and locks uncertain issues. The pending queue uses
the server's pending plus partially-dispensed default and follows bounded cursors;
failed/looping pages fail the view rather than return partial queue counts.

Request, supply and outcome attempts refresh the actual MAR, PRN, pharmacy,
patient-MAR and history roots. PRN keys include sanitized authorization scope.
Pagination errors leave request controls disabled. Policy and recorded indication
are clinical data and are never copied into audit metadata or logs.

## Regression evidence

`hms-db/tests/prn_doses.rs` tests real request/supply/outcome persistence, exact
replay and conflicting UUIDs, many-request and same-UUID races, interval and
rolling-limit boundaries, rechecking at administration, old generated courses,
stale snapshots, unconfigured orders, source/admission lock waits, unit changes,
stock overflow/expiry/location rules, refusal/hold history, scoped cursors and
transactional audit rollback. `hms-api/tests/prn_contract.rs` crosses the HTTP
handlers for typed payload, source visibility, authorization and uncertain errors.
Frontend tests use the real generated client/fetch boundary for request bodies,
AbortSignal, partial pages, uncertain writes, stock-basis preservation and admission
form isolation. This is implementation verification, not clinical approval.
